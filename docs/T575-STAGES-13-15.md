# SM-T575 LTE — Stage 13–15 checkpoint (2026-11-05)

## Verified Android measurements (Stage 13)
The owner's read-only test confirms:
- fb0 belongs to `16030000.decon_f`, reports 1200x1920,
  1200x3840 virtual, 4800-byte stride and 32-bit pixels.
- fb1 belongs to `16050000.decon_t`, reports 640x480,
  640x960 virtual, 2560-byte stride and 32-bit pixels.
- `bootloader_fb/reg` is 0xca000000 with length 0x01400000 (20 MiB).

These are observations of running Android and its DT, **not** measured
S-Boot display window, IDMA address, or proof of Linux framebuffer scanout.

## Stage 14: simpledrm source-level gate
The pinned Linux driver source uses
`of_reserved_mem_region_to_resource()` for the framebuffer's
`memory-region` property, which is permitted by the
`simple-framebuffer.yaml` binding. An audit has been added to
the DTB-only GitHub Actions workflow. The owner reported completion;
the GitHub connector did not independently expose a successful workflow
conclusion. Compilation and source-level consistency do not prove boot.

## Stage 15: restoration readiness (read-only)
Before contemplating even a reversible BOOT-only Linux attempt, the
working rooted Android state must be recoverable without wiping user
data or touching identity/modem partitions.

Run `python3 scripts/t575-stage15-restore-readiness.py` with one
authorized SM-T575 on ADB. It reports the *presence of selected
by-name partition links only*, without reading any partition content,
rebooting, flashing or changing Android. It deliberately always ends
with a BLOCKED verdict because link presence cannot prove recovery.

Requirements that cannot be cleared by this diagnostic:
1. Preserve the exact currently working Android BOOT and matched
   firmware images privately, with checked hashes.
2. Document and test a T575-specific rollback procedure (including
   Download-mode access and host flashing compatibility) without
   factory resetting, relocking, or overwriting identity partitions.
3. Establish original boot-header, DTB/DTBO-selection, Magisk,
   vbmeta and bootloader constraints before any experimental image.
4. Obtain evidence of S-Boot DECON window/IDMA base and safe display
   takeover that does not risk the powered display path.
5. Verify kernel build artifacts and actual CI results independently.

**No T575 Linux boot image is approved or produced.**
Do not use the inherited T570 installer or release images. Do not
touch EFS, sec_efs, RPMB, modem calibration, user data or bootloader
partitions. No Android modification is part of these stages.
